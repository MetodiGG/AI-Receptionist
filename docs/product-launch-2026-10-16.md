# GoRez product launch improvements — 16 October 2026

## Audit and boundaries

Existing Next.js 16.4 App Router / React 19.3, Supabase Auth + Postgres/RLS, Vercel and Resend are retained. Auth uses the same persistent client and exact existing `/account?lang=bg|en` and recovery callbacks. Server endpoints validate current users and business ownership; platform admin access remains the verified server allowlist. No credentials or new recipients are introduced.

Booking creation rechecks real availability, service duration, schedule/breaks and existing appointments, with database race guards. The confirmation, personal management link, customer history, notification outbox and 24-hour reminder worker are preserved. Reminder tests run offline, including real in-memory SQL queue tests. No customer emails or real booking mutations are needed for this release.

The assistant is deterministic, not a paid generative AI: published services/prices, hours/breaks, contact and rules; guided service/staff/date/slot/contact/review/explicit booking confirmation. Marketing now describes that actual scope. Existing illustrative photos are retained and labeled.

## Implemented

- One pricing source: `lib/product-config.mjs`, retaining `PRICE_LABEL`. Approved trial/price/no-card/no-automatic-charge terms appear on the home page, business landing, application and FAQ. No billing or trial enforcement is invented.
- Dedicated `/login`, shared Auth/session, admin detection, recovery link, sign-in/sign-up and existing-session continuation. Old `/?lang=…#business` bookmarks route safely to login and preserve query parameters; internal links now use `/login`. Recovery callback URLs are unchanged.
- Customer-first hero with both primary journeys, mobile navigation, existing photography/interactive illustrative flow, concise business CTA replacing the large home login form, useful footer and fixed `info@gorez.co` contact.
- Business landing: verified benefits, own link/QR, email reminders, clear setup steps, labeled interface example, actual guided-assistant scope, central pricing and FAQ. The application is explicitly not an activated account/profile.
- Four required application fields: business name, phone, email, category. Contact name, city and website/Instagram URL are optional. Shared client/server schema, phone/email checks, HTTP(S)-only URL, strict fields, origin guard, rate limit, body cap, hidden/non-focusable/autocomplete-off honeypot, duplicate protection, busy guard, accessible field errors and truthful saved-state confirmation. Existing admin mail is awaited, but mail failure never misrepresents a successfully saved application. No applicant-delivery claim is made.
- Directory: skeleton, timeout, error/retry, populated/empty/no-search-results states; no fabricated listings, no empty filters or public social-proof counters; categories/cities from actual public rows, names/services/durations/configured prices and real booking links. Existing server visibility checks (`active` and `platform_status=enabled`) remain.
- Future new business profiles start in “Awaiting approval”; owners can prepare services/team/schedule but cannot publish themselves. The existing service-only, audited administrator publication action checks setup readiness. Application approval is still separate from creating and publishing an actual profile. Existing businesses keep their current statuses and visibility.
- SEO: server-generated per-language titles/descriptions, self-canonicals, reciprocal `hreflang`/x-default, sitemap with only public business URLs, robots and private-route noindex headers. Public business metadata/structured data read only permitted public fields; no reviews, ratings or made-up opening hours. User text is JSON-LD escaped. No path-language migration.
- 1200×630 localized social-sharing graphics generated with the existing mark and palette; responsive image `sizes` prevents oversized logo requests. System fonts are retained, with no remote font service.
- Optional first-party funnel events, strict enum-only payload, no free-form metadata/URLs/account IDs/contact details, temporary in-memory flow key, UI and SQL deduplication, same-origin/rate checks, opt-in and revocation. **Disabled by default.** No new analytics provider. `business_signup_success` means an accepted application, not an Auth account or published profile; completed flows are not a replacement for actual booking counts. Existing operational business analytics remain separate and unchanged.

## Migration

`supabase/migrations/20261016180000_product_launch_foundation.sql` only relaxes NOT NULL for `partner_leads.contact_name` and `city` (existing length checks retained) and adds the private `product_events` table. Public and ordinary owners cannot read/write it; existing service-role server access is retained. No business, appointment, Auth, CRM or outbox change; no existing row is deleted or rewritten. Apply this migration **before** deploying optional form fields. In-memory PGlite tests execute the exact migration twice and verify preservation, validation, RLS/role isolation and deduplication.

`supabase/migrations/20261016180500_business_publication_review.sql` adds the `pending` moderation state, changes only the default for future business inserts and extends the owner-write guard. It does not update any existing business row or change existing bookings, Auth accounts, email configuration or outbox. Existing public APIs and the database booking guard already require `enabled`. Exact SQL tests verify repeatability, unchanged old visibility, default pending, forbidden owner bypasses, setup checks, audited service-role publication and booking protection.

## Configuration

- Existing domain, Supabase and Resend configuration stays unchanged. `NEXT_PUBLIC_APP_URL` should remain the canonical `https://www.gorez.co`.
- `COMPANY_NAME`, `COMPANY_EIK`, `COMPANY_ADDRESS`: provide only actual operator information; the identification block is shown only if all three exist. These are public identification values, not credentials. Do not invent them while the company is unregistered.
- `DPA_URL`: only a real reviewed HTTP(S) URL; otherwise no DPA link appears.
- `NEXT_PUBLIC_PRODUCT_ANALYTICS_ENABLED=true`: optional, requires migration, owner review of measurement/consent/retention and redeployment. Leave unset/false until then. Even enabled, no new funnel event is sent without affirmative opt-in. No persistent visitor identifier is stored; only the consent preference is saved locally. Infrastructure providers may still process request/security logs; do not advertise blanket anonymity or compliance.
- Event retention/cleanup is intentionally not scheduled or silently decided. Define retention and review privacy information before enabling measurement.

## Deferred decisions and risks

- No trial activation/expiry/paid-state columns or subscription management exist. Before implementing access changes, owner must define the start date, post-expiry access/new booking behavior, handling of existing bookings, reactivation, paid-consent evidence and retention. Never delete appointments on expiry. Current marketing describes the commercial offer; it does not imply automated enforcement or charging.
- Legal pages remain an explicitly provisional information baseline. Operator identity, contracts/DPA, provider disclosures, retention and onboarding terms need owner/legal review before broad commercial onboarding. Hiding an incomplete company block is not legal compliance.
- `/bg` and `/en` migration deferred: query language is retained to protect emailed recovery/account/booking/management/widget links. Future work needs route mapping, exact auth allowlist updates, legacy redirects preserving unrelated query parameters, no loops and full booking regression tests.
- Nearby discovery is design-only; see `nearby-discovery-proposal.md`. No Maps API, key, billing account, geolocation prompt or external listing was activated.
- No fake testimonials, ratings, partner logos or growth statistics. Existing example business records were not renamed or deleted; the owner should review which existing profiles are appropriate for public presentation.
- Production mutations and real email delivery are not tested by creating customer data. Build/tests and safe visual/read-only checks are reported separately. Lighthouse/lint/standalone TypeScript results must not be claimed if those tools/configurations are unavailable; the project is JavaScript and currently has no lint or standalone typecheck script.
